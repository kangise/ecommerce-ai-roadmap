# v1.3.0 Release Candidate

Date: 2026-08-26
Status: release candidate — local/runtime contract validation complete; external
acceptance remains explicitly conditional.

## Release scope and vertical gates

This candidate closes the implemented L0–L13 vertical path only where the
repository has an enforceable, persisted, tenant-scoped implementation and an
automated contract or runtime test. Each release gate requires the same chain:
data ownership/model, service/API, authentication and authorization, validation,
visible states, persistence after refresh, tests, build checks, and documented
operational limits.

| Gate | Candidate evidence |
| --- | --- |
| L0 | Versioned pilot contract, recovery rules, and no-mock/tenant ownership requirements. |
| L1–L4 | Tenant connector accounts, report recipes/sync, Evidence imports, and Metric Observation materialization with provenance and validation. |
| L5–L6 | Ads capability gate is fail-closed; this candidate registers no Ads write adapter, route, action, or operation. |
| L7–L9 | Published Agent Graphs, Daily Ops, Review/Proposal/approval/execution controls with durable lineage and audit. |
| L10 | Authenticated tenant Mission Control snapshot and bounded SSE with resume/reset/reconnect semantics. |
| L11 | One-process Pilot supervision, readiness/blockers, worker heartbeats, and loopback-by-default startup. |
| L12 | Per-tenant audit hash chain, Assurance runs, verified backup/restore, and restore assurance written only into a new target database. |
| L13 | Uniform 1.3.0 version contract, deterministic RC manifest, frozen changelog, supported-Python cold-wheel smoke, release checksums, and release/rollback procedure. |

## What is real in this candidate

- Runtime state is SQLite-backed, tenant-scoped, authorization-gated, and
  designed to survive refresh/restart according to the documented lease and
  recovery semantics.
- The runtime exposes the documented authenticated APIs, Pilot and worker
  controls, Assurance reads/evaluations, audit-chain verification, and recovery
  CLI. Backup includes the SQLite database and its evidence-object tree with
  manifest verification before restore.
- Mission Control and the embedded UI are connected to real runtime data; they
  do not use runtime mock dashboard metrics or fake connector delays.
- Assurance `eval` reports `blocked` when no eligible real workflow data exists;
  it does not turn empty data into a successful evaluation.

## Known limits and external blockers

- No Amazon Ads credentials, authorized account evidence, or external approval
  attestation are included here. L5 therefore remains blocked where those inputs
  are absent. L6 remains deliberately zero-write: no Ads write adapter, API
  route, action, or operation is shipped.
- Amazon SP-API and OpenAI live acceptance are external dependency checks. This
  release does not claim a live Amazon report import, Amazon Ads probe, or OpenAI
  model call without real deployment credentials and authorization.
- The Pilot, SSE connection accounting, and SQLite storage are single-process.
  They are not a distributed worker coordinator, multi-instance event broker,
  high-availability database, or horizontal-scale claim.
- Backups contain sensitive business and evidence data. The recovery CLI sets
  restrictive local permissions and verifies integrity, but it does **not**
  encrypt backups. Production storage encryption, key management, access control,
  retention, and off-host backup policy are mandatory external controls.
- Restore only targets a new, absent database/object directory after verification;
  it is not an in-place rollback command. Verify-only performs no target write.

## Candidate release procedure

1. Start from a clean reviewed worktree and record the exact candidate commit.
2. Run the repository gates available in this checkout:

   ```bash
   python3 scripts/build_dist.py --check
   python3 scripts/build_release_manifest.py --check
   python3 scripts/verify_all.py
   python3 -m pytest
   python3 integration/mcp-server.py --validate --dist dist
   ```

3. Build/package using the repository's normal release process. Install the
   wheel and its dependencies from a generated wheelhouse into a new virtual
   environment outside the checkout. Validate the installed CLI version, MCP,
   Schema v21, Demo end-to-end states, and backup verification there.
4. Stage the wheel, `dist` archive, RC manifest, this document, and the generated
   `SHA256SUMS` on a draft Release. Download the draft assets, verify the exact
   asset count and every checksum, and only then make the Release public. A
   failed upload or verification must leave the Release in draft state.
5. Deploy loopback-first behind TLS and an authenticated reverse proxy if a
   public bind is required. Configure secrets outside SQLite and verify Pilot
   readiness with a real viewer/admin key.
6. Before declaring external acceptance, collect real, tenant-authorized
   evidence for each enabled connector/provider. Record unavailable credentials,
   account permissions, or provider failures as blockers; do not substitute test
   fixtures or Demo data.

## Rollback and recovery

1. Stop the affected Pilot gracefully so workers release/finish their bounded
   work; retain logs, request IDs, and audit evidence.
2. Select a verified pre-deploy backup. Run `opc-ecommerce restore --verify-only`
   first, then restore into a new staging database path. The command refuses
   overwrite, symlink/traversal, manifest, checksum, schema, and integrity
   failures.
3. Validate the restored target's Assurance/audit-chain state and execute the
   candidate checks in staging before routing traffic to it.
4. Revert application/package deployment to the last validated release only
   after preserving the failed deployment evidence. Never delete or edit audit
   rows to make a rollback appear clean.

## Statements this RC must not make

- It must not claim Amazon Ads, SP-API, or OpenAI live success without recorded
  real credentials, authorization, and request evidence.
- It must not claim encrypted backups, distributed coordination, high
  availability, or multi-process SSE/worker guarantees.
- It must not claim signed provenance or an SBOM: v1.3.0 publishes SHA-256
  checksums, but artifact signing and SBOM generation remain future controls.
- It must not claim that Demo data, test fixtures, static checks, or a `201`
  Assurance response proves an external business workflow succeeded.
